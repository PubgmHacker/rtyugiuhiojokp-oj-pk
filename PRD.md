Ревизия 1.0 · арт-дирекшн подписан CPO · статус: в разработке

Документ задаёт требования к продукту уровня Tier-1: TMA внутри Telegram с
выходом в standalone (Capacitor 8 / App Store). Каждый раздел содержит

недопустимы — если требование нельзя проверить тестом или метрикой, это не

# 1. Визуал, стиль и дизайн-система

## 1.0 Решение об арт-дирекшне и что оно отменяет

CPO принял смену художественного направления: продукт уходит от холодной
нейтральной базы к **геймифицированной неоновой эстетике закрытого клуба**
(Dark Mode First, Sci-Fi / киберпанк-огранка).

Это решение прямо отменяет четыре пункта действующего закона из
`README.md:147-193`, и они должны быть переписаны в том же коммите, что и
токены, иначе документация начнёт врать:

| Отменяется | Чем заменяется |
|---|---|
| «Плоская заливка, без градиентов и цветных свечений» | Градиенты и свечения разрешены, но только в FX-слое (§1.3) |
| «Тени только нейтральные: цветной ореол — признак розового интерфейса» | Цветной ореол разрешён на активных состояниях, запрещён на статике |
| «Цветом обозначаем только действие и статус, всё остальное — оттенки серого» | Цвет несёт ещё и атмосферу; смысловая нагрузка цвета сохраняется (§1.2) |
| «Внимание должно доставаться фотографиям людей, а не интерфейсу» | Сохраняется как инвариант: FX не перекрывает медиа (§1.3, правило Z) |

Что **не** отменяется и остаётся жёстким: контраст AA, уважение
`prefers-reduced-motion`, отсутствие цвета как единственного носителя смысла,
единый источник токенов.

### Анти-паттерны («нейрослоп»), запрещённые к приёмке

Ревьюер обязан отклонить экран, если видит:

1. свечение на статичном, неинтерактивном элементе — неон обозначает
   интерактивность и состояние, иначе он превращается в фон;
2. более двух источников свечения в одном вьюпорте;
3. текст поверх градиента без сплошной подложки — контраст становится
   непроверяемым;
4. `backdrop-filter` внутри `backdrop-filter` (вложенное стекло) — мыло и
   просадка кадра;
5. фиолетово-розовый градиент как заливка крупной площади (это и есть
   «мыльный неон»); градиент допустим на площади ≤ 15 % вьюпорта или как
   обводка толщиной ≤ 2 px;
6. декоративная графика, сгенерированная ИИ, в продуктовых экранах. Ассеты —
   только из кода (`tools/brandmark.py`, `tools/make_icons.py`) или от
   дизайнера;
7. эмодзи в роли иконки интерфейса;
8. скругление больше `--radius-card` на вложенном элементе (пузырь внутри
   карточки не может быть круглее карточки).

## 1.1 Архитектура токенов: два слоя вместо одного

Причина разделения: контраст обязан быть проверяемым автоматически, а
свечение — отключаемым. Смешанные в одном слое, эти два требования конфликтуют
(нельзя посчитать контраст ореола, и нельзя погасить ореол, не тронув текст).

**Слой A — семантический (`--color-*`, существующий `@theme` в
`globals.css:17`).** Несёт смысл: фон, поверхности, текст, действие, статус.
Каждый токен слоя A проходит контрастный тест (§1.7). Свечений здесь нет.

**Слой B — FX (`--fx-*`, новый, объявляется в `:root` рядом с
`--glass-*` на `globals.css:130`).** Несёт атмосферу: ореолы, градиенты,
неоновые обводки, интенсивность стекла. Ни один токен слоя B не участвует в
передаче смысла и не проверяется на контраст, потому что поверх него никогда
нет текста. Любой токен слоя B может быть погашен в ноль — продукт остаётся
полностью работоспособным и читаемым.

```css
/* globals.css — новые токены слоя B */
:root {
  --fx-neon-primary:   #ff2d6f;  /* электрический розовый — действие */
  --fx-neon-secondary: #a855f7;  /* неоновый фиолетовый — симпатия */
  --fx-neon-tertiary:  #7c3aed;  /* фиалковый — премиум, редкость */
  --fx-glow-alpha: 0.55;         /* множитель всех ореолов: 0 = FX выключен */
  --fx-glow-blur: 24px;
  --fx-stroke-width: 1.5px;
  --fx-gradient-sympathy: linear-gradient(135deg, #ff2d6f 0%, #a855f7 100%);
  --fx-gradient-premium:  linear-gradient(135deg, #7c3aed 0%, #ff2d6f 100%);
  --glass-blur: 20px;            /* существует, переезжает под контроль tier */
}
```

Правило доступа: компонент читает `--color-*` для всего, что несёт смысл, и
`--fx-*` только для декора. Хардкод hex в TSX запрещён, как и раньше —
экраны собираются из `web/src/components/ui.tsx`.

## 1.2 Палитра

База углубляется относительно текущей (`#0a0b0f` → `#07070c`): клубная
темнота даёт неону работать, не поднимая общую яркость экрана.

| Роль | Токен | Значение | Требование к контрасту |
|---|---|---|---|
| Фон | `--color-bg` | `#07070c` | база отсчёта |
| Поверхность 1 / 2 / 3 | `--color-surface*` | `#12141c` / `#191c26` / `#222634` | ≥ 1.2:1 к соседней ступени (различимость границ) |
| Текст основной | `--color-text` | `#fafbff` | ≥ 12:1 на `--color-bg` |
| Текст вторичный | `--color-text-secondary` | `#c8cdd4` | ≥ 7:1 |
| Текст приглушённый | `--color-text-muted` | `#9ba1ab` | ≥ 4.5:1 |
| Текст слабый | `--color-text-faint` | `#868d96` | ≥ 4.5:1 (мелкий текст запрещён) |
| Действие | `--color-accent` | `#ff2d6f` | 4.5:1 на фоне — значение уже верифицировано в текущем README |
| Глиф на заливке | `--color-on-accent` | `#ffffff` | 4.6:1 на `--color-accent` — верифицировано |
| Симпатия / мэтч | `--color-accent-secondary` | `#a855f7` | ≥ 4.5:1 как текст; иначе только заливка с белым глифом |
| Лайк | `--color-success` | `#34d399` | ≥ 4.5:1 |
| Опасность | `--color-danger` | `#ff7a1a` | ≥ 4.5:1, отстоит от акцента на 25° по тону |
| Предупреждение | `--color-warn` | `#f0b429` | ≥ 4.5:1 |
| Верификация | `--color-info` | `#58a6ff` | ≥ 4.5:1 |

Существующие `--color-flame-start/end` и `--gradient-torch` (наследие торчевой
итерации) переименовываются в `--fx-*` и остаются как градиент премиума —
второй набор градиентных токенов в проекте не нужен.

Смысловая нагрузка цвета неизменна: розовый — действие, фиолетовый —
симпатия и премиум, зелёный — лайк, оранжевый — опасность. Ни одно состояние
не передаётся цветом в одиночку: у каждого есть форма, иконка или подпись.

## 1.3 Правила неона (ограничение CPO № 1)

Свечение — только декор и обводка активного состояния. Формализация:

**Правило Z (Z-порядок).** FX-слой живёт строго под контентом либо строго за
границей медиа. Ореол карточки рисуется через `::before` с отрицательным
`inset` и `filter: blur()`, но никогда не поверх фотографии или видео.
Технически: `z-index` FX-псевдоэлемента ниже `z-index` медиа-узла; проверяется
тестом на структуру DOM карточки.

**Правило одного источника.** В любой момент в вьюпорте светится не более
двух элементов: фокус пользователя (активная карточка, зажатая кнопка) и
индикатор таббара. Всё остальное гасится.

**Правило непроверяемого контраста.** Если поверх пикселя лежит текст,
свечение под ним запрещено. Текст всегда на сплошной подложке из слоя A.

**Разрешённые носители свечения**

| Элемент | Способ | Бюджет |
|---|---|---|
| Активная карточка деки | внешний ореол `::before`, `blur(var(--fx-glow-blur))` | 1 на экран |
| Кнопка в состоянии `:active` | `box-shadow` цветом действия, α = `--fx-glow-alpha` | на время нажатия |
| Индикатор таббара | обводка `--fx-stroke-width` + ореол | 1 на экран |
| Экран взаимной симпатии | `--fx-gradient-sympathy`, площадь ≤ 15 % | только этот экран |
| Премиум-бейдж, рамка карточки за наклейки | `--fx-gradient-premium`, обводка | ≤ 2 на экран |

**Запрещённые носители:** текстовые блоки, поля ввода, аватары, фото и видео
пользователей, служебные подписи, элементы списков в покое.

## 1.4 Glassmorphism: спецификация и цена кадра

Стекло существует (`--glass-bg`, `--glass-bg-strong`, `--glass-border`,
`--glass-blur` в `globals.css:130`) и остаётся, но переходит под контроль
класса устройства: `backdrop-filter` — самая дорогая операция в WebView, и на
среднем Android она стоит кадр.

| Слой | Применение | `backdrop-filter` |
|---|---|---|
| Стекло 1 | Таббар, шапка экрана | `blur(20px) saturate(160%)` |
| Стекло 2 | Шторка фильтров, модалки | `blur(20px) saturate(160%)` |
| Без стекла | Всё остальное | сплошная поверхность слоя A |

Ограничения, проверяемые ревью и тестом:

- максимум **два** стеклянных слоя одновременно в вьюпорте;
- вложенное стекло запрещено;
- у каждого стеклянного узла есть сплошной fallback того же контраста —
  при `--glass-blur: 0` экран выглядит целым, а не прозрачным;
- `will-change` не ставится на стеклянные узлы постоянно, только на время
  анимации: постоянный `will-change` держит слой в памяти GPU.

**Деградация по классу устройства.** `web/src/lib/deviceTier.ts` `[новый]`
определяет класс один раз за сессию по `navigator.hardwareConcurrency`,
`navigator.deviceMemory` и результату пробного замера кадра (30 кадров rAF
после первого пейнта):

| Класс | Условие | Что выключается |
|---|---|---|
| `high` | ≥ 6 ядер, ≥ 4 ГБ, кадр ≤ 10 мс | ничего |
| `mid` | ≥ 4 ядра, кадр ≤ 18 мс | `--fx-glow-alpha: 0.35`, частицы ≤ 10 |
| `low` | остальное | `--glass-blur: 0`, `--fx-glow-alpha: 0`, частицы выключены |

Класс пишется атрибутом `data-tier` на `<html>`; токены переопределяются
селектором, компоненты не правятся. Пользователь может понизить класс вручную
переключателем «Свечение» в профиле — повысить выше определённого нельзя.

## 1.5 Зонирование: где неон, где строгая утилита

Без явной границы неон расползается по всем экранам и продукт перестаёт
читаться. Граница проводится по функции экрана, а не по вкусу исполнителя.

**Зона A — дофамин.** Свайп-дека, лента Reels, экран взаимной симпатии,
витрина тарифов, кейсы и наклейки, онбординг-квест. Здесь работают ореолы,
градиенты, частицы, анимированные обводки. Задача зоны — атмосфера и вознаграждение.

**Зона B — утилита.** Экран переписки, список чатов, настройки, приватность,
жалоба и блокировка, платёжные экраны, юридические тексты. Здесь FX
ограничен точечными индикаторами. Задача зоны — прочитать и не ошибиться.

| Приём | Зона A | Зона B |
|---|---|---|
| Внешний ореол элемента | да | только онлайн-статус |
| Градиент как заливка | да, ≤ 15 % площади | нет |
| Неоновая обводка активного элемента | да | только активное поле ввода |
| Частицы (VFX) | да | нет |
| Анимированный бабл сообщения | — | да, см. ниже |
| Стекло | да | шапка и поле ввода |

**Мессенджер (зона B) детально.** Полотно переписки строго утилитарное:
сплошная поверхность `--color-surface`, текст `--color-text`, межстрочный
интервал 1.45, максимальная ширина строки 34 em. Новый стиль входит тремя
точками и только ими:

1. **Онлайн-статус** — точка 8 px цветом `--color-success` с ореолом
   `blur(6px)`, α = `--fx-glow-alpha`. Единственное свечение в переписке.
   При `data-tier="low"` — точка без ореола.
2. **Появление бабла** — входящий и исходящий пузырь появляются пружиной
   (§1.8): масштаб 0.94 → 1, прозрачность 0 → 1, смещение 8 px по вертикали.
   Никакого свечения у пузыря, никакого градиента: фон пузыря — сплошной
   (`--color-surface-2` входящий, `--color-accent` исходящий с белым глифом).
3. **Отправка** — микро-импульс обводки пузыря на 160 мс цветом действия,
   α ≤ 0.4. Это подтверждение отправки, а не украшение, и оно исчезает.

Тема переписки, выбранная парой (`api/services/chat_themes.py`,
`api/routers/chat_themes.py`), переопределяет **только** фон полотна и цвет
исходящего пузыря. Она не может включить ореолы, не может понизить контраст
текста ниже 4.5:1 и не может отменить правила выше — валидатор темы
отклоняет такую комбинацию на сервере, а не в клиенте.

## 1.6 Адаптивный оверлей ленты Reels

Проблема: управление лентой лежит поверх кадра, а кадр меняет яркость каждые
несколько секунд. Неоновая обводка на светлом кадре исчезает, тёмная иконка на
светлом кадре исчезает тоже. Решение — оверлей, который читает яркость кадра и
переключает режим.

**Измерение.** `web/src/lib/frameLuma.ts` `[новый]`. Каждые 400 мс (не каждый
кадр — это дешёвая операция, но не бесплатная) текущий кадр `<video>`
отрисовывается в offscreen-canvas 16×16 и считается взвешенная яркость по
Rec. 709 только в **зоне оверлея** (нижняя треть и правая колонка, где реально
лежат контролы), а не по всему кадру:

```
L = (0.2126·R + 0.7152·G + 0.0722·B) / 255,  усреднение по пикселям зоны
```

Гистерезис обязателен, иначе на видео с мерцанием оверлей начнёт
переключаться и это будет выглядеть как брак:

- `L > 0.62` два измерения подряд → режим `contrast`;
- `L < 0.48` два измерения подряд → режим `neon`;
- между порогами — режим не меняется.

Режим пишется атрибутом `data-overlay` на контейнер ленты; переключение
токенов — CSS-селектором, компоненты не знают о яркости:

| Токен | `data-overlay="neon"` (тёмный кадр) | `data-overlay="contrast"` (светлый кадр) |
|---|---|---|
| `--fx-glow-alpha` | `0.55` | `0` |
| Подложка контролов | нет | `rgb(7 7 12 / 0.55)` + `blur(8px)` |
| Обводка контролов | `--fx-neon-primary`, 1.5 px | `#07070c`, 1 px |
| Цвет глифа | `#fafbff` | `#fafbff` |
| Тень глифа | нет | `0 1px 2px rgb(0 0 0 / 0.6)` |
| Скрим кадра | `--gradient-scrim` (есть) | усиленный: α +0.15 |

Инвариант приёмки: **глиф и подпись остаются ≥ 4.5:1 к фактическому фону в
обоих режимах**. Проверяется тестом на синтетических кадрах — чёрный,
белый, полосатый 50/50, пересвеченное небо (§1.10). Отсутствие измерения (нет
доступа к кадру из-за CORS или закрытая вкладка) трактуется как `contrast`:
режим с подложкой читается всегда, режим с неоном — не всегда.

Стоимость: одно 16×16 чтение раз в 400 мс на активное видео. Только для
видимого элемента ленты; соседние предзагруженные видео не измеряются. При
`data-tier="low"` измерение выключено и режим фиксирован в `contrast`.

## 1.7 Субкультурная тема: от семи схем к матрице

CPO ставит задачу: выбор субкультуры в онбординге меняет оформление всего
приложения. Это сильная виральная механика, но при наивной реализации она
даёт комбинаторный взрыв: субкультур в фильтрах 23, схем оформления 7,
поддерживать 161 палитру невозможно.

**Решение — две независимые оси вместо одной.**

- Ось 1 `data-appearance` — **светлота и характер базы**: 7 существующих схем
  (classic, midnight, graphite, light, sepia, nebula, goldleaf). Отвечает за
  `--color-bg`, `--color-surface*`, `--color-text*`. Отвечает за читаемость.
- Ось 2 `data-vibe` `[новый]` — **субкультурный акцент и FX**: отвечает
  только за `--fx-*` и `--color-accent`/`--color-accent-secondary`. Отвечает
  за атмосферу.

Обе оси — независимые атрибуты на `<html>`. Комбинация валидна всегда, потому
что оси не пересекаются по токенам. Пользователь может носить готский акцент
на светлой базе, если ему так удобно читать.

**Стартовый набор vibe (6 штук, не 23).** Двадцать три субкультуры
маппятся в шесть визуальных семейств — большего рынок не различает, а
поддерживать шесть реально:

| `data-vibe` | Субкультуры | Акцент | FX-характер |
|---|---|---|---|
| `noir` | гот, метал, дарк, вампир | пурпур `#a855f7` | глубокий чёрный, ореол пурпурный, обводки тонкие |
| `acid` | Y2K, дрилл, хайп, рейв | кислотный `#39ff88` | хром: обводка светлая, ореол зелёный, высокая контрастность |
| `kawaii` | аниме, гик, k-pop, косплей | пастельный `#c084fc` | пастельно-фиолетовый, ореол мягкий и широкий |
| `street` | рэп, скейт, графити, спорт | оранжевый `#ff7a1a` | плотные плашки, ореол короткий, много контура |
| `alt` | эмо, панк, альт, нефор | малиновый `#ff2d6f` | базовый неон продукта |
| `clean` | без субкультуры / скрыл | малиновый `#ff2d6f` | FX приглушён: `--fx-glow-alpha: 0.3` |

`clean` — обязательный дефолт. Пользователь, не выбравший субкультуру,
получает нейтральный продукт, а не случайную тему.

**Правила, которые нельзя нарушить ни одному vibe:**

1. vibe не трогает `--color-text*`, `--color-bg`, `--color-surface*` — они
   принадлежат оси `data-appearance`. Поэтому смена субкультуры физически не
   может испортить контраст текста;
2. акцент каждого vibe обязан давать ≥ 4.5:1 на **всех семи** базах —
   произведение 6 × 7 = 42 пары проверяется тестом (§1.10), и это дёшево,
   потому что проверяются числа, а не скриншоты;
3. `acid` и `kawaii` на светлых базах (`light`, `sepia`) требуют затемнённого
   варианта акцента: пастель на белом фоне AA не проходит. Токен акцента
   объявляется дважды — под тёмные базы и под светлые, селектором
   `:root[data-appearance="light"][data-vibe="kawaii"]`;
4. смена vibe — мгновенная, без анимации перекраски всего экрана: переход
   цвета 4200 CSS-переменных выглядит как поломка. Допустима только
   кросс-фейд-накладка 180 мс поверх (§1.8).

**Виральность как измеримое требование.** Механика оправдана, только если
пользователь показывает её другим: экран выбора vibe умеет отдать
шаринг-карточку 1080×1920 с выбранной темой и знаком марки
(`web/src/lib/shareCard.ts` `[новый]`, растеризация через canvas, без
внешних сервисов). Метрика успеха — доля пользователей, поделившихся
карточкой, и D1 у этой доли против остальных (§5).

### 1.7.1 План рефакторинга семи схем (ограничение CPO № 3)

Текущее состояние: `globals.css:17` `@theme` — базовые токены; `:130` `:root`
— стекло и градиенты; `:509`–`:637` — шесть блоков `data-appearance` плюс
классика как база; сервер хранит выбор в `profile.app_theme`
(`api/services/appearance.py`, 38 строк); расхождение палитры лендинга и
мини-аппа ловит `test_лендинг_и_миниапп_не_расходятся_по_палитре`.

Рефакторинг — шесть шагов, каждый отдельный коммит, каждый оставляет продукт
рабочим:

**Шаг 1. Разделить слои, ничего не меняя визуально.** Ввести `--fx-*`,
перенести в них `--color-flame-start/end`, `--gradient-torch`, `--glass-*`.
Значения подобрать так, чтобы отрендеренный результат совпал с текущим до
пикселя. Приёмка: скриншотных изменений нет, тесты зелёные.

**Шаг 2. Углубить базу и перевести семь схем на новую палитру §1.2.** Правятся
только блоки `data-appearance`, экраны не трогаются. Приёмка: контрастный
тест на 7 схем × все текстовые токены.

**Шаг 3. Ввести ось `data-vibe` с единственным значением `clean`.** Атрибут
проставляется, селекторы работают, поведение не меняется. Приёмка: тесты
зелёные, `clean` идентичен шагу 2.

**Шаг 4. Добавить пять остальных vibe и матричный тест 6 × 7.** Здесь и
только здесь появляются новые цвета. Приёмка: 42 пары проходят AA.

**Шаг 5. Сервер.** `profile.app_theme` остаётся осью appearance; добавляется
`profile.app_vibe` + миграция Alembic + валидация значения по перечислению на
сервере (клиент не источник истины). Маппинг субкультура → vibe живёт в
`api/services/appearance.py` рядом со схемами, а не в клиенте, иначе бот и
мини-апп разойдутся. Приёмка: тест на то, что каждая из 23 субкультур
маппится в существующий vibe и что неизвестное значение даёт `clean`.

**Шаг 6. Онбординг проставляет vibe по выбранной субкультуре**, профиль даёт
сменить вручную и отвязать от субкультуры. Приёмка: e2e — выбор субкультуры в
онбординге меняет `data-vibe` без перезагрузки и переживает переустановку
приложения.

**Гейт всего рефакторинга:** `README.md:147-193` перезаписан под новый закон в
том же коммите, что и шаг 4; ни один экран не содержит хардкод-цвета
(проверяется линтом по `web/src`); тест расхождения лендинга и мини-аппа
расширен на `web/public` (§1.10).

## 1.8 Моушен-система и `prefers-reduced-motion` (ограничение CPO № 2)

**Пружины вместо таймингов.** Всё, что следует за пальцем или отвечает на
касание, описывается пружиной, а не `duration`+`easing`. Базовая пружина
проекта уже задана (`stiffness 380 / damping 34`) и остаётся каноном.

| Роль | Пружина | Где |
|---|---|---|
| Следование за пальцем | `stiffness 380 / damping 34` | карточка деки, шторки |
| Возврат в исходное | `stiffness 300 / damping 30` | отмена свайпа |
| Вылет карточки | `stiffness 220 / damping 26` | подтверждённый свайп |
| Появление элемента | `stiffness 420 / damping 38` | баблы, плитки, модалки |
| Индикатор таббара | `stiffness 500 / damping 40` | скольжение индикатора |

Жёсткие тайминги допустимы только там, где нет жеста: кросс-фейд смены темы
180 мс, импульс обводки при отправке 160 мс, вспышка VFX ≤ 380 мс.

**Редукция движения.** `prefers-reduced-motion: reduce` — не «чуть медленнее»,
а другая, полностью определённая ветка поведения. Требование CPO: сложные
анимации и микровзрывы заменяются простым изменением прозрачности.

| Обычный режим | При `reduce` |
|---|---|
| Микровзрыв частиц на лайке | fade-in→fade-out иконки-подтверждения, 160 мс, без движения |
| Вылет карточки по дуге с наклоном | fade-out карточки на месте, 140 мс |
| Пружинное появление бабла | fade-in, 120 мс, без масштаба и смещения |
| Скольжение индикатора таббара | мгновенная смена + fade 100 мс |
| Дышащий фон (два пятна, 40 с) | статичные пятна, анимация снята |
| Кросс-фейд смены темы | мгновенная смена без наложения |
| Пульсация ореола активной карточки | статичный ореол той же α |

Реализация: один хук `web/src/lib/motion.ts` `[новый]` отдаёт готовые
пресеты и сам подменяет ветку по `matchMedia('(prefers-reduced-motion: reduce)')`
с подпиской на изменение. Компоненты не проверяют медиа-запрос сами — иначе
половина забудет. Правило приёмки: **в `web/src` не существует ни одного
`transition`/`animate`, не проходящего через `motion.ts`** (проверяется линтом).

Отдельно: `reduce` **не** отключает FX-статику. Ореол, градиент и стекло —
это не движение, они остаются. Гасит их только `data-tier="low"` и
переключатель «Свечение».

## 1.9 Компоненты: кнопки действия, VFX, тактильный отклик

**Кнопки Лайк / Дизлайк / Суперлайк.** Три размера попадания: диаметр
касания ≥ 48 px (Лайк/Дизлайк) и ≥ 56 px (Суперлайк как главное платное
действие), визуальный диаметр может быть меньше. Состояния: покой →
`:active` (масштаб 0.94 + ореол цвета действия) → результат (VFX) →
блокировка на время сетевого запроса с сохранением места (никаких скачков
раскладки).

| Кнопка | Цвет | VFX при подтверждении |
|---|---|---|
| Лайк | `--color-success` | 14 частиц, разлёт 40–70 px, 320 мс |
| Дизлайк | `--color-text-muted` | без частиц: только `:active` и вылет карточки |
| Суперлайк | `--fx-gradient-premium` | 18 частиц + расходящееся кольцо, 380 мс |

Дизлайк намеренно без праздника: вознаграждать отказ — плохая продуктовая
механика, и это экономит кадр на самом частом действии.

**Движок частиц.** `web/src/lib/vfx.ts` `[новый]`. Требования:

- **один** пул на приложение: 24 предсозданных узла, переиспользуются;
  аллокаций на тапе нет;
- **один** общий `requestAnimationFrame`-цикл на всё приложение; цикл
  останавливается, когда активных вспышек нет (иначе телефон греется в покое);
- частицы рисуются `transform: translate3d()` + `opacity` — только
  композитные свойства, никаких `top/left/width`;
- бюджет: ≤ 18 частиц одновременно, время жизни ≤ 380 мс, суммарно ≤ 2 мс
  работы главного потока на вспышку;
- при `data-tier="mid"` — ≤ 10 частиц, при `low` и при `reduce` — путь
  частиц не запускается вовсе, вместо него ветка из §1.8.

**Тактильный отклик.** Обязателен на каждом действии, меняющем состояние.
Слой уже есть (`web/src/lib/haptics.ts`), в него добавляется карта событий;
TMA использует `Telegram.WebApp.HapticFeedback`, standalone — Capacitor
Haptics, отсутствие поддержки деградирует молча.

| Событие | TMA | Правило |
|---|---|---|
| Лайк | `impactOccurred('light')` | на подтверждении жеста, не на касании |
| Дизлайк | `selectionChanged()` | самый слабый отклик |
| Суперлайк | `impactOccurred('medium')` | |
| Мэтч | `notificationOccurred('success')` | один раз, вместе с экраном симпатии |
| Ошибка, лимит свайпов | `notificationOccurred('error')` | |
| Переключение таба, смена vibe | `selectionChanged()` | |

Запрещено: отклик на скролле ленты, на каждом кадре свайпа, на входящем
сообщении, когда приложение в фоне.

**Таббар.** Четыре раздела: Карточки · Видео · Чаты · Профиль. Кастомный,
стеклянный (стекло 1), индикатор скользит пружиной `500/40`, у активного
раздела — неоновая обводка и ореол (единственное свечение таббара).
Обязательно: `padding-bottom: env(safe-area-inset-bottom)`, счётчик
непрочитанных на «Чатах» с ограничением `99+`, состояние активного раздела
дублируется не только цветом (заливка иконки + подпись), иначе цвет
остаётся единственным носителем смысла.

# 2. Карточки и движок ранжирования (Matching Core)

## 2.1 Анатомия карточки

Карточка — главный носитель продукта, поэтому её слои фиксированы жёстко.
Снизу вверх:

1. **Медиа** — фото или первый кадр видео, `object-fit: cover`, соотношение
   3:4, ленивое декодирование, размытая LQIP-заглушка до загрузки (никогда
   пустой прямоугольник — он читается как сломанная карточка);
2. **Скрим** — `--gradient-scrim` (существует), только снизу, высота 38 %,
   нужен для читаемости подписей поверх любого фото;
3. **Контент** — имя, возраст, город, дистанция, чипы (цель, субкультура,
   рост), бейдж верификации, полоса заполненности профиля;
4. **Плашки жеста** — `LIKE` / `NOPE` / `SUPER`, появляются по прогрессу
   жеста (§2.2);
5. **FX-обводка** — неоновая обводка активной карточки, ореол через `::before`
   с отрицательным `inset`, **под** медиа по Z-порядку (правило Z, §1.3).

Инварианты: имя не переносится и обрезается эллипсисом; чипов на карточке
максимум 3, остальные — в деталях; тап по карточке открывает детали, а не
лайкает (двойной тап-лайк живёт в Reels, где нет кнопок под пальцем).

## 2.2 Физика свайпа

**Модель.** Жест не проигрывает анимацию — он двигает объект. Позиция
карточки во время касания равна смещению пальца один к одному, без инерции и
без сглаживания (любое сглаживание читается как «залипание»). Отпускание
передаёт управление пружине (§1.8) с текущей скоростью пальца как начальной.

```
progress = clamp(dx / (viewportWidth * 0.32), -1, 1)   // −1 нет … +1 лайк
angle    = progress * 9deg                              // наклон карточки
scaleNext = 0.94 + 0.06 * |progress|                    // карточка под ней подрастает
```

**Порог подтверждения** — по расстоянию **или** по скорости, что наступит
раньше: `|dx| > viewportWidth * 0.32` либо `|velocity| > 620 px/s`. Второе
условие обязательно: без него быстрый короткий флик не срабатывает, и жест
кажется тугим.

**Цветовая интерполяция (требование CPO).** По мере удаления от центра
карточка окрашивается — но окрашивается **обводка и скрим**, а не полотно с
фотографией: заливка поверх лица человека прямо противоречит инварианту
«внимание достаётся людям».

| Направление | Целевой цвет | Что окрашивается |
|---|---|---|
| Вправо (лайк) | `--fx-neon-primary` малиновый | обводка 2 px, ореол, плашка `LIKE`, скрим приобретает оттенок |
| Влево (отказ) | холодный графит `#2a2e3a` | та же обводка и скрим, ореол не зажигается |
| Вверх (суперлайк) | `--fx-gradient-premium` | обводка градиентом + кольцо |

Интенсивность: `alpha = |progress| * --fx-glow-alpha`, то есть при выключенном
FX (`low`, «Свечение» off) карточка меняет только толщину и цвет обводки —
жест остаётся читаемым без свечения. Плашка `LIKE`/`NOPE` появляется с
`opacity = clamp((|progress| - 0.15) / 0.35, 0, 1)` и масштабом
`0.9 + 0.1 * opacity`: до 15 % хода плашка не мигает от дрожания пальца.

**Бюджет кадра.** Во время жеста трогаются только `transform` и `opacity`
на карточке и её обводке. Запрещено: пересчёт лэйаута, чтение
`getBoundingClientRect()` в обработчике, изменение `box-shadow` покадрово
(тень интерполируется через `opacity` заранее отрисованного слоя), сетевые
запросы, тактильный отклик на каждом кадре. Цель: 58+ FPS на `mid`, 110+ FPS
при 120 Гц на `high`; замер — Performance-профиль на 20 свайпах подряд.

**Предзагрузка деки.** В DOM живут ровно три карточки: активная и две под
ней. Медиа следующих пяти профилей префетчатся. Когда в буфере остаётся
≤ 4 профиля, дека тянет следующую страницу — пользователь никогда не видит
спиннер посередине сессии свайпов.

## 2.3 Состояния карточки

| Состояние | Вид | Выход |
|---|---|---|
| `idle` | покой, обводка `--color-hairline` | касание → `dragging` |
| `dragging` | следует за пальцем, цвет по прогрессу | отпускание |
| `snapping-back` | пружина `300/30` в центр | → `idle` |
| `flying-out` | пружина `220/26` за границу + fade | → `committed` |
| `committed` | карточка удалена, решение отправлено оптимистично | ответ сервера |
| `rejected-by-server` | откат: карточка возвращается с плашкой ошибки | → `idle` |
| `limit-reached` | карточка не уходит, шторка лимита свайпов | покупка или ожидание |
| `reduce` | вместо вылета — fade-out на месте, 140 мс (§1.8) | → `committed` |

Оптимистичная отправка обязательна: ждать ответа сервера перед вылетом
карточки — это 200 мс паузы на каждом свайпе, то есть заметно медленный
продукт. Откат `rejected-by-server` — редкий путь, но он должен быть
реализован, а не проигнорирован.

## 2.4 Движок ранжирования

Сейчас порядок выдачи — случайная выборка (`matching.py:238-243`), а
`_compatibility` (`:124-144`) считает число только для показа. Требуется
переход к ранжированию. Переход обязан быть постепенным и обратимым.

### 2.4.1 Скрытый рейтинг привлекательности (ELO)

Каждому профилю — поле `Profile.elo` (по умолчанию 1400) и
`Profile.elo_updated_at`. Обновление по классической формуле при каждом
решении: свайп A по B трактуется как партия, где ставка — внимание.

```
E_b = 1 / (1 + 10^((R_a − R_b) / 400))        // ожидание, что B «выиграет» у A
S_b = 1.0 (лайк) | 1.3 (суперлайк) | 0.0 (отказ)
R_b' = R_b + K · w_a · (min(S_b, 1) − E_b)
```

- `K = 16` базовый; для профилей моложе 50 полученных решений `K = 32`
  (быстрая калибровка новичка), после 500 решений `K = 8` (стабилизация);
- `w_a` — вес голосующего: `w_a = clamp(R_a / 1400, 0.6, 1.6)`. Лайк от
  востребованного пользователя весит больше — иначе рейтинг накручивается
  массовыми лайками ботоводов;
- суточный дрейф одного профиля ограничен ±60 пунктов: защита от бригадинга;
- обновление **асинхронное**, батчем раз в 60 с из очереди, а не в транзакции
  свайпа: свайп не имеет права ждать пересчёта рейтинга.

**Этические и продуктовые ограничения, обязательные к соблюдению:**

1. ELO **никогда** не показывается пользователю — ни числом, ни буквой, ни
   намёком в интерфейсе. Публичный рейтинг привлекательности — репутационная
   катастрофа и прямой вред пользователю;
2. ELO не участвует в модерации, банах и ценообразовании;
3. ELO не сужает выдачу до касты: подбор идёт по **близости** рейтинга, а не
   по его величине (см. `f_elo` ниже), и полоса близости широкая;
4. профиль с недостаточной статистикой (< 20 решений) ранжируется как
   средний, а не как слабый.

### 2.4.2 Формула выдачи

Для каждого кандидата `p` считается балл. Все веса — в одном месте
(`api/services/ranking.py` `[новый]`, значения из БД-конфига, меняются без
деплоя, изменение логируется):

```
score(p) = ( w_elo·f_elo + w_geo·f_geo + w_act·f_act
           + w_rec·f_rec + w_cmp·f_cmp + w_sub·f_sub ) · m_boost · m_fresh
```

| Член | Формула | Смысл | Вес |
|---|---|---|---|
| `f_elo` | `1 − min(|R_p − R_me| / 400, 1)` | близость рейтинга, не величина | 0.20 |
| `f_geo` | `1 − min(d / d_max, 1)`, `d` — км | ближе лучше, обрыв на пользовательском лимите | 0.22 |
| `f_act` | таблица §2.4.3 | способность ответить | 0.18 |
| `f_rec` | `like_back_rate(p)` за 30 дней, нормировано | взаимность, а не популярность | 0.12 |
| `f_cmp` | существующий `_compatibility`, нормированный в 0…1 | интересы, цель, тип связи | 0.16 |
| `f_sub` | §2.4.4 | субкультура и интересы | 0.12 |
| `m_boost` | `1.6` при активном платном бусте, иначе `1.0` | купленный буст | — |
| `m_fresh` | §2.4.5 | буст новичка | — |

Порядок применения фильтров строгий и не обсуждается: **сначала жёсткие
фильтры** (пол и кого ищем, возрастные рамки, дистанция, блокировки, баны,
скрытые анкеты, уже просмотренные, `is_paused`), **потом** ранжирование
остатка. Ни один множитель не имеет права протащить в выдачу профиль,
отфильтрованный жёстко.

**Миграция с случайной выборки.** Существующий `Profile.sample_key` не
удаляется: он становится детерминированным тай-брейкером внутри одного
балльного бакета, чтобы выдача не дёргалась между страницами. Выдача
собирается бакетами по 0.05 балла, внутри бакета — порядок по `sample_key`.
Раскатка через флаг `ranking_enabled` на процент пользователей, метрика
сравнения — доля свайпов, дошедших до мэтча, и D1 (§5).

### 2.4.3 Пессимизация мёртвых анкет

Главный вред неактивной анкеты — не пустая выдача, а потраченный лайк и
написанное сообщение без ответа. Поэтому активность входит в формулу весомо и
на крайних значениях действует как фильтр:

| `last_active_at` | `f_act` | Дополнительно |
|---|---|---|
| < 24 ч | 1.00 | — |
| < 72 ч | 0.75 | — |
| < 7 дней | 0.45 | — |
| < 30 дней | 0.15 | скрывается из выдачи для платных пользователей |
| < 60 дней | 0.05 | письмо/пуш «вас лайкнули» — попытка вернуть |
| ≥ 60 дней | **исключён** | помечается `dormant`, возвращается в выдачу при первом входе |

Дополнительный сигнал `f_act` умножается на `0.6`, если у профиля
`unanswered_ratio > 0.8` за 14 дней (получает сообщения и не отвечает):
формально активен, фактически тупик для собеседника.

### 2.4.4 Субкультурный множитель и защита от пузыря

```
f_sub = min(1, 0.55·совпадение_vibe + 0.30·(|общие_интересы| / 4)
              + 0.15·совпадение_субкультуры_точное)
```

`совпадение_vibe` — 1, если vibe кандидата совпадает с моим (§1.7),
0.5 — если vibe из смежного семейства (`alt`↔`noir`, `acid`↔`street`), иначе 0.

**Защита от пузыря — инъекция контраста.** Внутри каждой страницы деки ровно
одна карточка (то есть ≤ 1 из 7) выбирается из «противоположного» пула:
`f_sub` для неё игнорируется, а vibe берётся из заведомо не смежного
семейства. Пример пар для инъекции: `alt` ↔ `street`, `noir` ↔ `kawaii`,
`acid` ↔ `clean`.

Ограничения инъекции, без которых механика превращается в баг:

1. инъекция **не** ослабляет жёсткие фильтры: возраст, пол и кого ищем,
   дистанция, блокировки, баны соблюдаются полностью. «Для фана» — только
   поверх безопасного множества;
2. инъекция не работает у пользователя, который явно сузил фильтр по
   субкультуре руками: он заплатил вниманием за выбор, и подмена — обман;
3. частота инъекции адаптивная: если пользователь три страницы подряд
   отказывает контрастным карточкам, доля падает до 1 из 14, ещё три — до
   нуля на 7 дней. Продукт обязан слышать «нет»;
4. доля инъекции и её конверсия — отдельные события аналитики (§5), иначе
   механику невозможно ни защитить, ни закрыть.

### 2.4.5 Буст новичка (первые 24 часа)

Цель — довести нового пользователя до первого мэтча в первую сессию: это
сильнейший предиктор D1.

```
m_fresh = 1 + 0.8 · max(0, 1 − hours_since_signup / 24)
```

Плюс гарантия объёма, а не только множитель: **не менее 150 показов и не
менее 25 показов платным пользователям** в первые 24 часа. Если органика не
добирает — профиль догоняется в выдаче принудительно, с приоритетом по
незаполненности других слотов.

Защита от перекоса: суммарная доля новичков на одной странице деки ≤ 30 %,
иначе опытные пользователи получают ленту одних пустых анкет. Буст новичка
не применяется, если анкета не прошла модерацию, без фото или заполнена
менее чем на 60 % — иначе механика разгоняет мусор.

## 2.5 Лимиты, защита от накрутки

| Правило | Значение |
|---|---|
| Свайпов в сутки, free | 60 (после — шторка тарифа) |
| Свайпов, Plus и выше | без лимита, но rate-limit 1 решение / 300 мс |
| Суперлайков в сутки | по тарифу (`services/plans.py: superlikes_for`), free — 1 |
| Инъекция контраста | ≤ 1 на 7 карточек, адаптивно вниз |
| Дрейф ELO в сутки | ±60 |
| Массовый лайк (>200 лайков/час, like_rate > 0.9) | ELO-вес `w_a` → 0.6, флаг модерации |

Механика «Перемотка» (отмена последнего отказа) — новая: квота по тарифу,
хранение последнего решения в течение 10 минут, откат через
`api/routers/likes.py` с восстановлением профиля в дек на позицию 1. Отмена
**мэтча** невозможна: это функция блокировки, а не перемотки.

## 2.6 Гейты приёмки Блока 2

| Гейт | Проверка |
|---|---|
| Жёсткие фильтры не обходятся ничем | тест: инъекция контраста и буст новичка на наборе с блокировками и возрастными рамками не протаскивают ни один профиль |
| ELO не утекает в API-ответ | тест: ни один сериализатор не содержит `elo` |
| Мёртвые анкеты не показываются платным | тест на `f_act` по всем ступеням таблицы |
| Порядок стабилен между страницами | тест: две последовательные страницы не пересекаются и не меняют порядок |
| Свайп держит кадр | Performance-профиль, 20 свайпов, ≥ 58 FPS на `mid` |
| Цвет жеста работает при выключенном FX | vitest: при `--fx-glow-alpha: 0` обводка меняет цвет и толщину |
| Ранжирование откатывается флагом | тест: `ranking_enabled=false` возвращает прежнюю случайную выдачу |
| Веса меняются без деплоя | тест: изменение конфига меняет порядок без перезапуска |
