Проект собирается локально: `./tools/ios-build.sh simulator` уже проходит.

## 2. Подготовка в Apple Developer Portal

1. **Аккаунт.** Нужен платный Apple Developer Program (99 $/год). Для
   dating-приложения выгоднее оформить на организацию: приложения от
   Individual чаще получают дополнительные вопросы при ревью.
2. **Bundle ID.** Зарегистрируйте `com.simp.dating` (Identifiers →
   App IDs). Включите Capability **Push Notifications**.
3. **APNs-ключ.** Keys → создайте ключ с Apple Push Notifications service,
   скачайте `.p8` (скачать можно один раз). Сохраните Key ID и Team ID —
   они понадобятся бэкенду для отправки пушей.
4. **Team ID.** Membership → Team ID. Он нужен скрипту архивации.

## 3. Сборка и загрузка

```bash
# Проверка, что всё собирается (без подписи)
./tools/ios-build.sh simulator

# Архив для App Store (нужна настроенная подпись)
DEVELOPMENT_TEAM=XXXXXXXXXX ./tools/ios-build.sh archive
```

Скрипт сам соберёт веб-бандл, синхронизирует его с нативным проектом,
создаст `.xcarchive` и экспортирует `.ipa` в `build/ios/`.

Загрузка в App Store Connect:

```bash
xcrun altool --upload-app -f build/ios/App.ipa -t ios \
  --apiKey <KEY_ID> --apiIssuer <ISSUER_ID>
```

Ключ App Store Connect API создаётся в App Store Connect → Users and
Access → Integrations. Альтернатива — приложение Transporter или
Xcode → Product → Archive → Distribute App.

Перед каждой загрузкой поднимайте `CURRENT_PROJECT_VERSION` (build
number): App Store Connect не принимает повторную загрузку с тем же
номером.

## 4. Метаданные в App Store Connect

**Возрастной рейтинг: 18+.** Обязательно отметьте в анкете рейтинга
«Frequent/Intense Sexual Content or Nudity» → *None*, но категорию
Dating указать необходимо. Прежнего уровня 17+ в анкете больше нет:
Apple перешла на шкалу 4+ / 9+ / 13+ / 16+ / 18+, и сервисы знакомств
с чатом и пользовательским контентом попадают в 18+.

**Рейтинг магазина и порог регистрации совпадают: 18.** Это разные
вещи — рейтинг 18+ описывает, кому App Store отдаёт приложение
(родительский контроль на устройстве), а порог регистрации — кого сервис
пускает в анкету, — но ревьюер открывает оферту по обязательной ссылке
EULA и сверяет одно с другим. Раньше порог был ниже, и на этот вопрос
пришлось бы отвечать в Resolution Center с отклонённой сборкой на руках;
теперь регистрация с 18 лет везде, где порог записан: `api/config.py`
(`MIN_AGE` — единственный источник для валидации API), `bot/config.py`
и тексты бота (`bot/texts.py`), онбординг и вход мини-аппа
(`web/src/pages/Onboarding.tsx`, `Login.tsx`), оферта
(`landing/terms.html`), политика (`landing/privacy.html`), правила
(`landing/guidelines.html`), лендинг, `web/public/manifest.json`
и README. Аудитория от этого уже, зато расхождения, о котором спрашивает
ревью, больше не существует.

От рассинхрона страхует `api/tests/test_age_floor.py`: он читает
`MIN_AGE` из конфига и сверяет с ним каждый из этих текстов, включая этот
файл. Менять порог — значит поменять `MIN_AGE` и прогнать этот тест: он
перечислит все места, где число осталось старым.

**Категория:** Primary — Social Networking, Secondary — Lifestyle.

**Обязательные URL** (разверните `landing/` и подставьте реальный домен):
- Privacy Policy URL → `https://simp.app/privacy.html`
- Terms of Use (EULA) → `https://simp.app/terms.html`
- Support URL → `https://simp.app/support.html`
- Marketing URL → `https://simp.app/`

**App Privacy.** Заполните Nutrition Labels строго в соответствии с
`PrivacyInfo.xcprivacy`: имя, фото, приблизительное местоположение,
идентификатор пользователя, пользовательский контент — всё «связано с
пользователем», отслеживание отсутствует.

**Скриншоты.** Обязательны для 6.9″ (iPhone 17 Pro Max, 1320×2868) и
6.5″ (1284×2778). Нужно 3–10 штук: дека, экран мэтча, чат, профиль,
настройки. Проще всего снять на симуляторе:

```bash
xcrun simctl boot "iPhone 17 Pro Max"
xcrun simctl io booted screenshot shot1.png
```

Скриншоты не должны содержать реальных лиц без прав на использование и
не должны обещать функции, которых нет.

## 5. Что чаще всего приводит к отклонению

**Guideline 1.2 — User Generated Content.** Для приложений с UGC нужны
все четыре механизма, и ревьюер их проверяет вручную:
- фильтрация недопустимого контента (у нас — AI-модерация фото и текста);
- механизм жалобы на контент;
- блокировка пользователя;
- контактные данные для обращений.

Все четыре реализованы, но убедитесь, что жалоба и блокировка доступны
не более чем в два тапа из чата и из профиля, и что модерация реально
работает на продакшене (задан `ZHIPU_API_KEY`, иначе останется только
фильтр по ключевым словам).

**Guideline 3.1.1 — In-App Purchase.** Закрыто: подписка в iOS продаётся
через StoreKit 2, сервер проверяет подпись Apple и начисляет уровень.
Внешняя оплата (Telegram Stars, CryptoBot) остаётся только в вебе и в боте.

Сюда же относится платная досрочная разблокировка бана (349 ₽, Telegram
Stars в боте): кнопка на экране «Доступ закрыт» показывается только внутри
Telegram (`isInTelegram()` в `web/src/pages/Banned.tsx`). В нативной сборке
её нет и быть не должно — ссылка из iOS-приложения на внешнюю оплату это
прямое нарушение 3.1.1. Забаненному в iOS остаётся «Оспорить блокировку»
(письмо в поддержку) — этого для ревью достаточно.

Что нужно сделать в App Store Connect перед релизом:
1. Создайте одну группу подписок и **девять** продуктов — по три срока на
   каждый платный уровень:

   | Уровень | Месяц | 3 месяца | Год |
   |---|---|---|---|
   | Plus | `com.simp.dating.plus.monthly` | `...plus.quarterly` | `...plus.yearly` |
   | Ultra | `com.simp.dating.ultra.monthly` | `...ultra.quarterly` | `...ultra.yearly` |
   | Aurora | `com.simp.dating.aurora.monthly` | `...aurora.quarterly` | `...aurora.yearly` |

   Идентификаторы заданы в `api/services/plans.py` (`Plan.appstore_id`), а не
   переменными окружения: продукт — это уровень плюс срок, одной парой
   «месяц/год» линейка не описывается. Сервер сопоставляет чек с тарифом
   через `plan_for_appstore_id`, поэтому незнакомый идентификатор просто не
   зачтётся.
2. В группе задайте порядок уровней: Aurora выше Ultra, Ultra выше Plus.
   По нему Apple решает, применять смену подписки сразу (повышение) или в
   конце оплаченного периода (понижение). Перепутанный порядок задержал бы
   покупку верхнего уровня, хотя деньги уже списаны.
3. Заполните `APPSTORE_APP_APPLE_ID` в `.env` — числовой Apple ID
   приложения. Без него проверка чеков не включится, и кнопка покупки не
   появится (это защита: иначе оплата прошла бы, а подписка нет).
4. Для TestFlight и App Review поставьте `APPSTORE_USE_SANDBOX=true` —
   их покупки живут в песочнице.
5. Локально покупки тестируются без App Store Connect: в Xcode откройте
   Product → Scheme → Edit Scheme → Options → StoreKit Configuration и
   выберите `web/ios/App/Simp.storekit`. Этот файл собран из линейки, и
   его совпадение с ней стережёт `api/tests/test_appstore.py` — правьте
   тарифы в `plans.py`, а не в нём.

Восстановление покупок есть на экране профиля — ревьюер проверяет этот
пункт отдельно.

**Возвраты и отзывы покупок.** В App Store Connect в разделе App
Information → App Store Server Notifications укажите URL
`https://<домен>/api/iap/appstore/notifications` (версия V2). Подпись
уведомления проверяется тем же верификатором, что и чеки, — адрес
открытый, и без проверки любой прислал бы поддельный REFUND и погасил
подписку кому угодно. По REFUND и REVOKE доступ закрывается сразу; без
этого возврат замечался только в момент, когда клиент сам предъявлял чек.

**Guideline 4.8 — Sign in with Apple.** Реализован: `POST /api/auth/apple`
принимает identity-токен и проверяет его по-настоящему — подпись ключом
Apple (RS256, ключи с `appleid.apple.com/auth/keys`), издателя, аудиторию
(наш bundle id) и срок годности (`api/services/apple_auth.py`). Аккаунт
заводится по `apple_id` без `telegram_id`: у пришедшего из App Store
Telegram может не быть вовсе. Забаненный не получает чистую историю —
список банов проверяется и здесь.

Клиент готов: плагин `web/native-plugins/capacitor-apple-signin`, кнопка
на экране входа (первой, как требует Apple), право
`com.apple.developer.applesignin` в `web/ios/App/App/App.entitlements` и
`CODE_SIGN_ENTITLEMENTS` в обеих конфигурациях Xcode. Имя и почту Apple
отдаёт только при ПЕРВОМ входе и только если человек их разрешил — плагин
запрашивает их сразу, иначе получить их потом уже нельзя.

Что нужно сделать в кабинете (кодом не решается): включить возможность
Sign in with Apple у App ID в Apple Developer Portal и убедиться, что
профиль подписи её содержит. Без этого запрос падает в рантайме с
`ASAuthorizationError`.

Проверено: `xcodebuild` собирает приложение с плагином без ошибок, класс
плагина линкуется в бинарник, `CODE_SIGN_ENTITLEMENTS` виден в настройках
сборки. Целостность цепочки закрыта тестом
`test_вход_через_apple_собран_целиком`.

**Guideline 5.1.1(v) — удаление аккаунта.** Реализовано: Профиль →
Удалить аккаунт, с подтверждением. Проверьте, что серверный
`DELETE /profiles/me` действительно удаляет данные, а не помечает флагом.

**Демо-доступ.** Ревьюеру нужен рабочий вход без Telegram Mini App.
В нативной сборке экран входа принимает одноразовый код: команда `/link`
у бота выдаёт шестизначный код, он вводится в приложении и обменивается
на сессию (`POST /api/auth/link`, код живёт 10 минут и работает один раз).
Заранее заведите аккаунт с заполненной анкетой, а в App Review
Information либо приложите свежий код, либо опишите путь через бота —
код с коротким сроком жизни к моменту ревью истечёт, поэтому надёжнее
описать процедуру. Пустая дека при первом входе выглядит как
неработающее приложение — заполните базу тестовыми анкетами.

## 7. Пуш-уведомления

Готовы обе стороны. Осталось только завести ключ:

1. Apple Developer Portal → Keys → создайте ключ с Apple Push
   Notifications service, скачайте `.p8` (доступно один раз).
2. Заполните в `.env`: `APNS_KEY_P8` (содержимое файла, переводы строк
   как `\n`), `APNS_KEY_ID`, `APNS_TEAM_ID`, `APNS_BUNDLE_ID`.
3. Для сборок из Xcode и TestFlight поставьте `APNS_USE_SANDBOX=true` —
   их токены живут в песочнице, прод-хост отвечает `BadDeviceToken`.

Пока ключ не задан, приложение работает как раньше: уведомления приходят
только внутри Telegram.

Что делает сервер: принимает токен устройства (`POST /profiles/me/devices`,
таблица `dating_device_tokens`), отправляет уведомление при новом мэтче и
при сообщении собеседнику, которого нет в чате. Токены, на которые Apple
ответила «приложение удалено», вычищаются автоматически. Уведомления из
одного чата схлопываются в одно (`apns-collapse-id`), сброс бейджа уже
делает клиент при открытии списка чатов.
